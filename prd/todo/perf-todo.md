## 一、实测基准

### 1.1 内存（任务管理器里的 29.4MB 只是主进程）

开发模式（`pnpm dev`，调试版，React 开发构建）下，port-helper 完整的进程树如下：

| 进程 | 类型 | 私有内存 | 工作集 |
| --- | --- | --- | --- |
| port-helper.exe | 主进程（Rust） | 39.7 MB | 80.3 MB |
| msedgewebview2.exe | 浏览器主进程 | 73.4 MB | 183.8 MB |
| msedgewebview2.exe | GPU 进程 | **108.1 MB** | 91.8 MB |
| msedgewebview2.exe | 渲染进程（页面） | **86.5 MB** | 139.1 MB |
| msedgewebview2.exe | utility × 2 | 20.6 MB | 68.3 MB |
| msedgewebview2.exe | crashpad | 3.2 MB | 17.6 MB |
| **合计** | 7 个进程 | **≈ 331 MB** | ≈ 581 MB |

- 发布版主进程：私有内存 39.7 MB / 工作集 71.2 MB / 43 个线程；可执行文件 3.5 MB。
- **测量口径**：任务管理器默认的“内存”列是主进程的**私有工作集**，所以显示 29.4MB；它既不包含 WebView2 子进程，也和上表的“私有内存”不是同一个指标。
- **测量限制**：测发布版时，开发版实例还在运行，两者共用同一个 WebView2 数据目录（`dev.porthelper.app`），所以发布版复用了开发版的 WebView2 进程，没能单独测出发布版的 WebView2 内存（见 P0-1）。

### 1.2 后端耗时（发布版，15 次取中位数）

测试环境：365 个进程，252 条端口记录，127 个服务。

| 阶段 | 耗时 |
| --- | --- |
| 读取端口表 `net::list_all` | 0.45 ms |
| 读取服务列表 `service_map` | 0.36 ms |
| sysinfo 全量刷新基础信息 | 6.6 ms |
| `ProcessCatalog::load` | 14.4 ms（其中约 7.8 ms 是第二次刷新：只取指定 PID 的路径、命令行时，sysinfo 内部又把全部进程枚举了一遍） |
| `query_port` 全流程 | 16.0 ms |
| `get_process_detail` 全流程 | 17.2 ms（又做了一次完整的进程快照） |

复测命令：`cargo test --manifest-path backend/Cargo.toml --release --test perf_probe -- --ignored --nocapture`

### P1：内存，收益最大

- [x] **P1-1 窗口最小化或隐藏时，把 WebView2 的内存目标调为“低”**（`backend/src/memory.rs`；效果待实测）
  - 依据：wry 0.57 提供 `set_memory_usage_level`（对应 WebView2 的 `MemoryUsageTargetLevel`，要求 Runtime 114 及以上，更低版本调用后不生效）。Tauri 可以通过 `webview.with_webview` 拿到底层 WebView 调用。
  - 方案：
    - 监听窗口事件，最小化或隐藏时设为 `Low`，恢复显示时设回 `Normal`；
    - 设为 `Low` 前先停掉前端的计时器和动画（目前页面没有轮询，影响很小）。
  - 预期收益：窗口在后台时渲染进程和 GPU 进程释放部分内存，具体数值需实测。
  - 风险：低。恢复窗口时可能需要重新绘制，首帧略慢。
- [ ] **P1-2 试验 WebView2 启动参数，减少 GPU 进程内存**（实验项，必须 A/B 对比；脚本已支持 `-BrowserArgs`，待测量后决定是否采用）
  - 依据：开发模式下 GPU 进程占 108MB，是单项最大；本应用界面简单，只有柔光一个持续动画。
  - 方案：
    - 在 `tauri.conf.json` 的窗口配置里加 `additionalBrowserArgs`；
    - 自定义后会覆盖默认值，必须保留 `--disable-features=msWebOOUI,msPdfOOUI,msSmartScreenProtection`；
    - 依次试验 `--disable-gpu`、`--disable-gpu-compositing`，每次测 P0-1 的三个场景，同时记录 CPU 占用。
  - 预期收益：可能明显降低 GPU 进程内存，需实测。
  - 风险：中。改为软件渲染后，动画、滚动的 CPU 占用可能上升，高分屏下可能出现模糊或卡顿。效果不明确就不采用。

### P1：后端重复计算

- [x] **P1-3 合并“端口查询”和“进程详情”两次请求**（已删除 `get_process_detail`）
  - 依据：详情面板每次选中进程或刷新时，都会单独调用 `get_process_detail`，再做一次完整的进程快照（17ms）。一次刷新后端实际做了两遍，合计约 33ms。
  - 方案：`query_port` 在已有快照上直接返回每个进程的命令行、工作目录和父进程链；前端详情面板优先使用查询结果，不再单独请求。`get_process_detail` 只保留给单独查看详情的场景。
  - 预期收益：每次刷新的后端耗时约 33ms 降到 16ms，前后端通信次数减半。
  - 风险：低。返回数据会略大（每个进程多几百字节）。
- [x] **P1-4 消除进程快照里的第二次全量枚举**（实际方案见“实施记录”）
  - 依据：`ProcessCatalog::load` 14.4ms 中约 7.8ms 是重复枚举。
  - 方案 A（改动小）：端口查询不需要父进程链，只调用一次只刷新目标 PID 的方法，不再先做全量刷新。预计降到约 8ms。
  - 方案 B（改动大）：用 `CreateToolhelp32Snapshot` 一次拿到所有进程的 PID、父 PID 和名称；对目标 PID 用 `QueryFullProcessImageNameW` 取路径，用 `NtQueryInformationProcess(ProcessCommandLineInformation)` 取命令行；只有工作目录继续用 sysinfo。预计约 2–3ms。
  - 预期收益：用户基本感知不到（16ms 已经很快），主要是减少 CPU 占用和内存分配抖动。**建议先做方案 A**。
  - 风险：方案 B 要自己处理权限不足、32/64 位进程等兼容问题，需要补测试。
- [x] **P1-5 操作前的安全校验只读单个进程**
  - 依据：`ops::guard` 为了校验一个 PID，会加载全量进程快照和服务表（约 14ms），但实际只需要名称和启动时间。
  - 方案：改为只读取目标 PID 的名称和启动时间；只有判断是否为服务时才读服务表。
  - 预期收益：关闭和强制结束的响应时间约少 10ms。风险低。

### P2：主进程

- [x] **P2-1 限制 Tokio 运行时线程数**
  - 依据：发布版主进程有 43 个线程。Tauri 默认的多线程运行时会按 CPU 核数创建工作线程，而本应用的命令都会放到阻塞线程池执行，并不需要这么多工作线程。
  - 方案：用 `tauri::async_runtime::set` 自定义运行时：工作线程 2 个，阻塞线程池上限 4 个。
  - 预期收益：减少线程栈占用的内存，约 1–3MB，需实测。风险低。
- [x] **P2-2 sysinfo 只开启需要的模块**
  - 依据：sysinfo 默认还开启了磁盘、网络、温度传感器、用户等模块，本项目都用不到（已确认没有引入 rayon 线程池）。
  - 方案：`sysinfo = { default-features = false, features = ["system"] }`。
  - 预期收益：可执行文件和编译时间略减，对内存影响可以忽略。风险低。

### P2：前端

- [x] **P2-3 设置页和确认框按需加载**
  - 依据：生产包 416KB（gzip 后 128KB），目前全部在启动时解析。
  - 方案：用 `React.lazy` 拆分设置页和确认框；进程反查页、设置页在首次访问时才挂载（目前三个页面启动时全部挂载、隐藏常驻）。
  - 预期收益：启动解析时间和页面常驻内存略减，需实测，预计只有几 MB。
- [x] **P2-4 输入时不重渲染整页**
  - 依据：输入框的值放在页面组件里，每输入一个字符，都会让结果卡片和详情面板一起重新渲染。
  - 方案：输入值下沉到 `Composer` 组件内部，只在提交时上报；`ProcessCard` 用 `memo` 包起来。
  - 预期收益：结果少时几乎没有差别，记录多时（例如显示全部状态）输入更跟手。
- [x] **P2-5 关闭倒计时的刷新频率**
  - 依据：等待进程退出时，倒计时每 200ms 重新渲染一次弹窗。
  - 方案：进度条改用一次性的 CSS 过渡动画，剩余秒数改为每秒更新一次。收益很小，顺手优化即可。

## 三、实施记录（2026-10-06）

### 3.1 已实测的效果

| 项目 | 优化前 | 优化后 | 说明 |
| --- | --- | --- | --- |
| 进程信息快照 `ProcessCatalog::load` | 14.4 ms | **8.3 ms** | 每次查询只做一次全量枚举 |
| 端口查询全流程 | 16.0 ms（不含详情） | **8.3 ms**（含详情） | — |
| 一次刷新的后端总耗时 | 约 33 ms（查询 + 详情） | **约 8.3 ms** | 前后端通信从 2 次减为 1 次 |
| 关闭/结束前的安全校验 | 约 14 ms | **0.03 ms** | 只读取目标进程 |
| 启动时加载的 JS | 420.7 KB（gzip 129 KB） | **355.8 KB**（gzip 约 111 KB） | 设置页、进程反查页、各确认框改为按需加载 |
| 发布版可执行文件 | 3.51 MB | 3.65 MB | 新增 webview2-com 与独立 tokio 运行时依赖 |

### 3.2 与原计划不同的地方

- **P1-4**：原计划的方案 B（用 ToolHelp 快照代替 sysinfo）实测无效：ToolHelp 快照本身也要 7.1ms，而 sysinfo 读取单个进程的路径、命令行、工作目录只额外花 0.15ms。**真正的成本是“全量枚举”本身（约 7ms）**。最终方案是：用 `NtQueryInformationProcess` 逐级查询目标进程的父 PID，再把“目标进程 + 祖先”一次性交给 sysinfo 刷新，每次查询只做一次全量枚举。
- **P1-5 附带修复**：进程已退出但仍有句柄未关闭时，内核对象还在、能被打开，新的校验曾误报为“PID 被复用”。现在读取启动时间时会一并检查退出时间，已退出就视为不存在。
- **父进程链附带改进**：父进程退出后 PID 可能被新进程复用；如果“父进程”比子进程启动得还晚，就不再把它当作父进程。
- **P2-4 附带修复**：设置页按需加载时，同一个加载边界里已显示的进程反查页被临时隐藏，重新显示后输入框被清空。现在每个页面使用各自的加载边界，输入框也只在写入序号变化时才覆盖内容。

## 四、明确不建议做的

| 方案 | 不做的原因 |
| --- | --- |
| 换用 mimalloc 等内存分配器 | 在 Windows 上通常会让常驻内存变高，与目标相反 |
| 把 React 换成更轻的框架 | 收益只有 JS 堆的几 MB，重写成本大，主要内存在 WebView2 进程本身 |
| 缓存端口查询结果 | 端口占用是实时信息，缓存会导致“端口已释放但界面还显示占用”的误判；16ms 的耗时也不需要缓存 |
| 处理日志文件增长 | 已确认 tauri-plugin-log 默认单个文件最大 40KB、只保留一份，不会无限增长 |

## 五、建议执行顺序

1. **P0-1**：建立基准。
2. **P1-1**、**P1-3**、**P1-5**：风险低，收益明确。
3. **P1-2**：A/B 试验，根据数据决定是否采用。
4. **P1-4** 方案 A，以及 **P2-1**、**P2-2**。
5. 前端 P2 项按需进行。
